# 我的抽卡记录：前端交互与统计说明

日期：2026-09-09。状态：交互规格，尚未实现。后端契约以 [后端开发计划](./gacha-records-backend-plan.md) 和后续 OpenAPI 为准；本文不指定视觉风格或前端组件库。

## 1. 页面结构

独立页面“我的抽卡记录”，复用现有子账号选择。默认显示该子账号当前游戏，允许切换查看原游戏历史；不自动合并多个子账号的结果。

页面层次：全卡池总览 → 卡池统计卡片/列表 → 单池详情和编辑。全局筛选包括游戏、卡池类型及实际出金日期；单池详情也可以直接进入。

全卡池主指标建议为“已记录抽数”“出金数”“平均出金抽数”“不歪率”。卡池列表显示名称、开放区间、类型和相同口径的简要统计；不适用不歪率的卡池不显示 0%。

“全卡池”是当前选定子账号和游戏内的全部卡池。常驻、特殊抽取结果计入总抽数和金数，普通 UP 不歪率只计算适用的普通 UP 池。

## 2. 单池详情

- 展示该池已记录抽数、金数、平均间隔、不歪率及样本数；UP 数/总 UP 占比可以作为次要信息。
- 按实际出金顺序显示每一金的密探、间隔抽数、UP/非 UP、出金前是否必 UP，以及可选日期/备注。
- 提供“记录出金”“编辑记录”操作。常驻/特殊池根据已知规则显示适用内容。
- 额外自选奖励独立区域展示，不能和出金记录排在同一个保底序列中。
- 可以展示出金间隔图、密探分布；不用欧非评分，不单独突出“歪的次数”。

不显示“更新垫抽”按钮、实时垫抽输入、距离下一金剩余抽数。用户不会被要求逐次更新未出金抽数。可在录入区域显示“下一条记录必 UP”，它表示已保存序列的结果约束，不是实时游戏进度。

## 3. 初次记录与出金表单

先选择卡池。卡池来自用户可用目录，支持搜索已经结束的池；普通池没有已公开 UP 成员时不供新建记录选择。目录找不到密探时提示等待管理员补齐，不向个人用户提供公共目录创建能力。

普通 UP 池首次建立档案，填写“首条记录是否处于必 UP 状态”。这是一次性的序列起始条件，不是垫抽数。中途开始记录同样填写；开池默认值只有在该池规则已经确认后才能预填。

出金表单：

| 输入 | 交互 |
| --- | --- |
| 结果密探 | 选择一位该游戏已发布的绝密密探 |
| 本次出金抽数 | 必填整数；普通 UP 为 1～40；直接抄游戏记录显示的“X 抽出金” |
| 实际获得时间 | 可选；输入和展示用北京时间，提交时带时区 |
| 备注 | 可选 |

“本次出金抽数”包含出金这一抽；第一条也填写游戏记录中的该次间隔，不填本池累计抽数。不提供“未知抽数”，也不把空白转换为 0。

出金前不是必 UP：结果候选为该游戏已发布的绝密密探，本池 UP 置前。出金前必 UP：只允许选择本池 UP 密探。UP 标记自动显示，不让用户随意勾选覆盖。

常驻/特殊池不套用普通 UP 候选限制。额外自选使用独立表单选择密探和已确认的奖励档位，不要求填写“这次用了几抽”，也不把 300 当作新增投入。

## 4. 编辑、删除、补录与排序

用户在本地修改一份单池档案草稿，一个保存按钮提交最终列表：

- 可编辑每条密探、抽数、日期和备注。
- 可删除条目；删除后立即重算后续状态。
- 可在指定位置补录历史出金，不默认把补录时间当作出金顺序。
- 支持拖动排序，并提供明确的上移/下移操作供其他交互方式使用。
- 编辑起始保底状态后重算完整列表。

每条记录 ID 始终保留。数组顺序即实际出金顺序，不按 `created_at` 或有缺失的日期自行重排。

修改前面记录可能让后面原先合法的选择失效：保留原有选择并标出冲突，不静默换成另一个 UP，也不自动删掉该行。提示例如“第 3 金应为 UP，请检查前面的结果、顺序或漏记”。有明确冲突时阻止保存；后端仍做最终校验。

第一版列表代表一段连续出金记录。只记自己关心的几金可能让保底推导和不歪率不准确，首次录入处简要说明。系统不能仅靠抽数验证所有漏记。

## 5. 保存与失败反馈

- 加载时保存服务器 `revision`，提交时带 `expected_revision`；修改同一份草稿的网络重试使用原 `request_id` 和原正文。
- 保存成功，以服务端返回的最终列表、revision、推导状态和统计更新页面。
- 校验失败，按后端返回的记录 ID/位置定位错误，保留用户未保存内容。
- 版本冲突表示网页其他窗口或 AstrBot 已修改该池。提示重新读取并处理本地修改，不自动以旧表单覆盖服务端。
- 响应丢失时允许重试原请求，不重新生成记录 ID；后端去重避免重复出金。
- 清空最终 `records` 表示删除该池所有出金；`selection_rewards` 仍独立处理。提交前清楚展示这次删除影响。

补录/删除/排序属于前端交互；持久保存、账号归属和最终规则校验属于后端。不能因为前端候选已经过滤就跳过后端校验。

## 6. 统计展示口径

“已记录抽数”仅等于各条出金间隔之和，不包含最后一金后的垫抽。平均值是已记录出金间隔的平均，不声称覆盖用户全部实际投入。

“不歪率”是非必 UP 状态下获得 UP 的次数 / 非必 UP 判定次数，歪后必 UP 那一金不参与分子或分母。显示如 `60%（3/5 次）`，无判定样本时显示“暂无数据”。

示例：甲池 1/1 不歪、乙池 1/9 不歪，全卡池应显示 2/10=20%，不能平均两个百分比。全池平均出金抽数同样用总抽数除以总金数，不平均各池均值。统计以服务端响应为准。

无实际日期的记录仍计入默认总览；启用日期筛选时不计入，并提示排除了多少条无日期记录。筛选后的不歪率仍沿用完整历史推导出的前置状态，不从窗口第一条重新开始。

自选奖励单独计数，可以在密探分布中区分“抽取获得”和“自选获得”；不额外增加 300 抽，不算一金，不影响不歪率。无需为了记录一项奖励补造抽取记录。

## 7. 目录调整与导入导出

卡池改名或延期后显示最新公共资料，个人结果不变。卡池/密探已删除时显示历史回退名称和“目录条目已删除”，不让用户历史变成空白。用户不能通过编辑私有快照改写公共目录。

导出以完整池档案为单位，保留初始状态、顺序、稳定 ID、日期及奖励；不把筛选后零散记录当作完整池档案导出。

导入先选择目标子账号，展示将新增/覆盖的池；明确是覆盖文件列出的池，其他池不动。显示规则冲突和目录缺失信息，确认具体影响后提交。文件解析和预览可以先在前端完成，后端提交时仍统一校验并原子保存。

## 8. 交付核对

实现时验证：同一池在网页和 AstrBot 查询到相同顺序及统计；前置记录修改能提示后续冲突；无样本不显示 0%；未知日期不被误标为录入日期；自选奖励不混入出金；没有垫抽或未知抽数入口。接口定稿后以真实错误和响应示例补充对接部分。
