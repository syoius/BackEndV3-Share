# 密探目录 UP 卡池与草稿发布：后端开发计划

日期：2026-09-09。状态：方案记录，尚未实现。本文整理本次讨论确认的行为；接口路径、服务及集合命名为实施建议，正式契约以后端实现和 OpenAPI 为准。

AstrBot 的功能范围单独记录在 [AstrBot 卡池接入功能记录](./operator-catalog-up-pools-astrbot-notes.md)。

个人出金记录、单池与全池统计见 [个人抽卡记录后端计划](./gacha-records-backend-plan.md)。加入该需求后，本计划同时提供用户侧卡池查询并保留个人历史引用；抽卡记录仍独立于公共目录保存。

## 1. 已确定的目标

- 卡池资料仍存入各密探的 `operator_catalog` 文档，不另建卡池内容主表。
- `up_pools` 按游戏分层；游戏只有 `如鸢`、`代号鸢`。同一密探可以在两个游戏先后 UP。
- 一次开放是一条卡池记录；实装、各次复刻使用不同 `pool_id`。同一次开放的所有 UP 密探共享 `pool_id`。
- 密探编辑页支持编辑普通资料和卡池，一个保存按钮、一个组合请求，后端事务内全部保存。
- 独立卡池管理页支持查询、新建、编辑名称和时间、调整 UP 成员、删除卡池、添加复刻；时间和成员可以一次保存。
- 未找到的名称自动创建密探：ID 按录入顺序分配，稀有度默认 5，游戏取本次卡池游戏，其余资料允许暂缺。
- 新密探可以作为草稿持续维护，用户侧图鉴和养成不能看到或使用草稿；由管理员补齐并发布。
- `operator_catalog` 是密探元数据的唯一来源；库存心纸目录、关注及导入校验读取其中已发布的密探，不另存或同步密探目录副本。
- AstrBot 可通过管理员授权的集成接口查询、新建和修改卡池，使用与前端相同的业务逻辑。
- 普通 UP 卡池供个人抽卡记录按 pool_id 引用；常驻、自 BAN 和额外自选特殊池不分发到密探 up_pools，由抽卡模块另行维护轻量条目。

本期不实现公告抓取/OCR、不自动发布密探、不按卡池时间触发发布、不引入卡池内容的第二份权威存储。

## 3. 数据模型

下面为对外 JSON 示例；Kotlin 属性和 Mongo 字段沿用项目命名规则，不要求把现有字段统一重命名。

```json
{
  "id": "char_126_auto",
  "name": "示例密探",
  "rarity": 5,
  "games": ["如鸢", "代号鸢"],
  "publication_status": "draft",
  "up_pools": {
    "如鸢": [
      {
        "pool_id": "pool_example_a",
        "name": "示例卡池",
        "start_at": "2026-09-10T05:00:00+08:00",
        "end_at": "2026-09-24T05:00:00+08:00"
      }
    ],
    "代号鸢": []
  }
}
```

约定：

1. 响应中的 `up_pools` 固定返回两个游戏键，没有记录时为 `[]`；旧文档缺失字段按空集合读取。
2. `pool_id` 为服务端生成的全局稳定 ID，代表某一游戏的一次开放。同名、同时间都不是身份键。
3. 同一密探中一个 `pool_id` 至多出现一次；跨密探副本的游戏、名称、起止时间必须一致。
4. 同一次卡池不能跨游戏。新建后游戏保持不变；录错游戏通过删除并重新创建修正。
5. 卡池游戏必须包含在成员的 `games` 中，添加关联时取并集。移除关联不自动删减 `games`。
6. 编辑普通资料不得移除仍有卡池关联的游戏，应返回明确错误，由管理员先处理关联。
7. 时间输入必须带时区；前端使用北京时间 `+08:00`，后端存 `Instant`，卡池 DTO 统一按 `+08:00` 输出。其他已有 API 的时间格式不因此改变。
8. `start_at < end_at`，开放区间为 `[start_at, end_at)`。允许录入历史、未来和彼此重叠的卡池，不用名称去重或禁止重叠。
9. 普通编辑不接收整个 `up_pools` 快照作为覆盖命令。修改使用 `pool_id`，移除关联与删除整次卡池是两种不同操作。

复刻不需要额外的父卡池或复刻次数字段：管理界面可复制已有表单再新建，后端生成新的 ID。

## 4. 草稿、发布与校验

### 4.1 状态规则

- 新建请求和自动创建默认 `draft`；已有文档缺失状态字段以及原有种子条目解释为 `published`。
- 发布状态表示目录是否公开，不表示官方是否已经实装，也不随卡池时间自动变化。
- 首版支持 `draft -> published`；不提供 `published -> draft` 普通切换，避免影响已有个人记录。
- 添加卡池、上传头像、修改资料、插件请求不隐式发布。
- 管理端可查看两种状态，并返回 `incomplete_fields`；用户侧只使用已发布条目。

### 4.2 保存与发布校验

草稿仍要求有效 ID、非空名称、合法稀有度、非空且受支持的 `games`。允许 `prof=[]`、奇闻名称为 `null`、其他可选列表为空；填写的值仍校验类型、长度、范围和已有关系规则。

自动创建默认：`rarity=5`、`games=[game]`、`prof/subProf/discs/starStones=[]`，别名、奇闻名称、头像、SP 本体关系为 `null`。不根据名字猜职业、奇闻或 SP 关系。

显式发布至少要求 `prof` 非空、第三项奇闻名称有效，并通过已有基础字段校验。扩展 `incomplete_fields` 反映这两个发布必需字段；头像等可选资料不作为发布门槛。发布 SP 时其本体也必须已经发布。

已发布条目不能主动清空已有的发布必需资料。现有项目已经允许历史条目缺失奇闻名称：这些条目保持公开并继续显示待维护提示，卡池编辑不得因此被拦截；普通资料编辑允许保留原有缺失值，不新增缺失。新草稿发布则完整执行发布校验。

### 4.3 后端可见性

分别提供明确的管理查询与已发布查询，不把管理端查草稿的方法直接用于用户业务：

- 公共目录过滤草稿；管理员和授权集成查询可以返回草稿。
- 用户养成导入（含 v3 自动采集）、局部校正、标注、目标、快捷提升均拒绝草稿 ID，使用各接口既有的未知/不可用密探错误契约。
- SP 反向索引与自动关联仅含可公开使用的关系，不能因导入本体而创建草稿 SP 的个人记录。
- 核对当前养成、公开分享、导出等路径，不新增草稿投影；不删除或重写既有个人历史数据。
- 为“我的抽卡记录”提供用户侧卡池列表/详情，普通 UP 部分复用聚合查询并过滤草稿成员；全部 UP 成员均未发布的卡池不供新建个人记录选择。公共密探条目仍只返回自己的卡池，不携带其他成员资料。

## 5. 名称匹配与 ID 分配

每个输入成员使用 `{ "id": "..." }` 或 `{ "name": "..." }`，两种形式择一：

- ID 输入严格按 ID 定位；找不到返回错误，不转为自动创建。
- 名称去除首尾空白后，在全目录（含草稿、所有游戏）按 `name` 精确查找。
- 唯一匹配复用已有 ID；零匹配创建草稿；多个匹配返回候选 ID，由调用方明确选择。
- 不自动匹配别名、拼音或模糊近似名称。成员解析后按 ID 检查重复；同批重复名称不产生多个密探。
- 复用已有密探时只合并游戏及写入卡池，不用自动创建默认值覆盖其资料或状态。

自动 ID 使用 `char_<数字>_auto`，数字从现有 ID 的最大数字段之后分配，至少补齐三位。用户已接受按录入顺序编号；它不是实际发布日期，补录老密探不会重排旧 ID。

建议用一个持久计数器原子分配，不在每次创建时执行无锁 `max + 1`。首次初始化读取现有目录；手工指定 ID 的新建也推进计数器下界，并避免已使用数字段再次分配。保留业务 ID 唯一索引。事务回滚允许编号有空缺，不要求连续。

计数器初始化前完成目录播种，避免第一条自动草稿使空库播种被跳过。对资源后来新增的同编号不同后缀，不按名字自动改写已发出的业务 ID，实施时应明确报告冲突。

## 6. 卡池服务及统一保存

建议新增 `OperatorPoolService` 和组合编辑服务，所有入口调用同一套事务内业务方法，不在服务间发 HTTP 请求。

| 操作 | 语义 |
| --- | --- |
| 新建 | 分配 `pool_id`，解析/创建成员，向每位密探写入完整卡池副本 |
| 修改 | 按 `pool_id` 更新所有成员的共享字段；可同时增减成员 |
| 移除当前密探关联 | 只删除这一位的副本；其他成员保持关联 |
| 删除整次卡池 | 移除所有副本，不删除密探或其游戏归属 |
| 复刻 | 新建新 ID；旧卡池不变 |
| 查询 | 从密探文档按游戏展开、按 `pool_id` 聚合，返回卡池资料及 UP 成员 |

卡池应至少有一个成员。只剩一位时，单独移除关联返回错误，提示执行整次卡池删除。既有密探删除接口也需要处理其卡池关系：有其他成员则保留卡池，最后一个成员被删则该卡池随之消失；不改动既有个人历史数据。

个人抽卡记录开始引用 pool_id 后，删除卡池/成员/密探不得级联删除用户出金记录。个人模块保存必要的历史展示资料和已验证结果归类，公共对象缺失时仍可展示历史；公共改名或延期不修改用户抽数、结果和顺序，成员调整也不静默重算既有历史归类。详见个人抽卡计划的历史保留与导入规则。

卡池编辑采用局部更新：字段缺失保留；名称和时间显式 `null` 无效。`up_operators` 缺失表示不改成员，提供时表示最终完整成员列表；`null` 和空列表无效。

组合保存建议请求包含可选 `profile` 和 `pool_changes`：`profile` 使用专用局部资料 DTO；卡池变更使用显式的 `create/update/attach/detach` 操作列表，不全量覆盖数组。`attach` 按已有 `pool_id` 关联当前密探；共享字段修改影响全部成员。重复操作同一卡池应拒绝而非依赖列表顺序猜测结果。

密探编辑页不暴露删除整次卡池按钮；修改共享资料时展示受影响成员数。组合响应返回当前密探及受影响的卡池/成员 ID，便于前端刷新。

普通资料、头像更新仍需改成仅写自身拥有的字段，或在适当事务中读取并保留最新卡池/状态，避免旧实体整体保存覆盖其他入口刚提交的卡池。未提交字段不得重置。

## 7. 事务、重试与版本

- 组合保存、卡池创建/修改/删除均使用已有 Hub Mongo 事务。校验、成员解析、新密探、各卡池副本、幂等结果要么一起提交，要么一起回滚；不能降级为部分成功。
- 对同一卡池的成员变更和共享字段修改，事务内基于最新成员集合执行；保证并发操作不能留下资料不同的副本。集成测试覆盖一次改成员与一次延期交错的实际入口。
- 创建请求携带稳定 `request_id`；含创建操作的组合请求同样携带。建议幂等范围为管理员用户 ID + 操作类别 + `request_id`，允许更换 Token 后重试。
- 持久保存规范化请求业务字段和创建结果，直接比较字段，不使用内容哈希。相同请求返回原创建结果；同键不同内容返回 `409 request_conflict`。仅存幂等结果，不用它作为卡池查询主表。
- 幂等结果与写入在同一事务中落库，唯一索引防止重复创建。卡池后来编辑或删除后，重放旧创建请求仍不重新创建；需要最新状态另行查询。
- 对包含按名称新增成员的编辑，保留同样的请求去重能力，避免响应丢失后因成员后来改名而重复创建。
- 同一事务内变更使用一个目录版本，事务失败不发布新版本、不提前刷新 SP 缓存。沿用已有目录版本机制，不加指纹；公开目录变化后版本必须更新，重启后仍可读回。
- 种子初始化放在业务事务之前；新增代码不得在事务中混入头像文件写入。组合保存不包含头像二进制上传。

## 8. 建议接口

所有路径均为计划，实施时在 OpenAPI 定稿；现有普通资料接口继续保留。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /v1/admin/operator-catalog` | 管理目录，含草稿、卡池和待维护字段 |
| `PATCH /v1/admin/operator-catalog/{operatorId}/edit` | 资料与卡池操作的组合保存 |
| `POST /v1/admin/operator-catalog/{operatorId}/publish` | 显式发布；重复发布返回当前结果 |
| `GET /v1/admin/operator-pools?game=如鸢` | 聚合列表，支持名称和时间范围查询 |
| `GET /v1/admin/operator-pools/{poolId}` | 卡池详情与完整成员 |
| `POST /v1/admin/operator-pools` | 新建卡池、必要时创建草稿 |
| `PATCH /v1/admin/operator-pools/{poolId}` | 一次修改资料和成员，也可只修改时间 |
| `DELETE /v1/admin/operator-pools/{poolId}` | 删除整次卡池 |
| `GET /v1/operator/catalog` | 原有公开目录，只含已发布密探及各自卡池 |
| `GET /v1/gacha/pools` | 抽卡模块的用户侧可记录卡池列表，普通 UP 聚合本服务、其他类型来自轻量目录 |
| `GET /v1/gacha/pools/{poolId}` | 公开卡池资料和可见成员，不包含任何个人抽卡记录或统计 |

列表时间范围采用与查询窗口相交的语义：`pool.start_at < to && pool.end_at > from`，边界缺失时不限制该端；默认按开始时间、ID 稳定排序。卡池名称不唯一，查询可返回多个候选。

管理接口沿用 JWT 与 `operator_catalog:write`。新字段使用 snake_case；原有显式 JSON 字段映射保持原样。

错误沿用当前 `OperatorErrorResponse` / 各控制器响应约定，新增领域码建议为：`pool_not_found`（404）、`request_conflict`（409）、`ambiguous_operator_name`（409）、`invalid_pool_time`（422）、`empty_up_operators`（422）、`operator_incomplete`（422）。权限错误仍为 401/403。详细字段路径和候选只向有权限的管理/集成调用者返回。

## 9. 密探目录作为唯一来源

此部分遵循 [库存后端规范](./standards/inventory/backend-design.md)、[交换协议 v1](./standards/inventory/exchange-protocol-v1.md) 及其 [Schema](./standards/inventory/schema/inventory-exchange-v1.schema.json)。

目前管理员维护的密探目录与库存的 `entity_catalog` 分别初始化，新增或改名没有自动同步。本次选择消除重复来源：库存 API 保持原有用途和响应结构，其 `agent` 部分直接投影已发布密探；不再采用发布时同步副本的方案。

### 9.1 查询、校验及版本

1. `EntityCatalogService.catalog()` 的 `item` 部分继续读取 `entity_catalog`；`agent` 部分调用密探目录的已发布查询，映射为 `{ entity_type: "agent", id: operatorId, name }`，不暴露管理字段。
2. `exists("agent", id)` 只判断该 ID 是否为已发布密探；`exists("item", id)` 保持原查询。心纸关注与库存导入复用该入口，不能再直接查旧 `agent` 行作为后备来源。
3. 新密探发布后立即可用于心纸目录、关注和库存导入；改名直接反映到目录响应。无需登记、复制或同步另一条密探元数据。
4. 草稿即使在旧 `entity_catalog` 中有同 ID 记录也不能绕过过滤。目录发布状态不改变库存数量、历史奖励或既有关注记录；不能以隐藏目录为由删除这些个人事实。
5. 保持现有目录响应的对象类型和 ID 排序；前端仍可自行按 ID 数字段排序，无需第二份目录。
6. 库存目录 `catalog_version` 组合物品目录版本与密探目录版本，使任一来源变化都反映到返回值；直接组合版本字符串，不加哈希、不仅取两个版本中的较大值。不能继续只使用首次播种时的内存日期。
7. 普通用户的库存导入仍只按稳定 ID 校验，不因 `entries[].name` 自动创建或改写目录。权威名称来自密探目录，历史记录中的名称仍按既有协议保留。

### 9.2 初始化与存量处理

- 停止在 `EntityCatalogService` 播种 `inventory/operators.json`，只保留物品播种；移除该重复密探资源及其运行时引用。密探统一由 `operator/operators.json` 初始化、由管理员目录维护。
- 首次请求即使来自库存，也必须通过密探目录服务完成所需的初始化，不能直接查尚未播种的仓储而返回空密探列表。
- 切换前对实际库做一次按 ID 的差异核对，目的是发现旧 `entity_catalog.agent` 独有的对象，避免仅依据两份种子相同就让现有对象消失。若确有独有条目，先确认是否为需保留的实际密探，再按原 ID 补入唯一目录；两边都有的条目以管理员密探目录为准，不用旧副本覆盖名称。
- 需要保留且原已对用户可见的旧条目，按历史已发布条目处理，缺失职业/奇闻继续标记待维护。明确属于已删除密探的旧副本不能因切换重新创建。
- 旧 `entity_catalog.agent` 行切换后不再读写或作为兜底；可以暂时留在库中，无需为启用新功能执行破坏性清理。物品条目不变。
- 不修改当前库存、奖励历史、快照基线和 `record_id` 幂等规则；不更换密探 ID，不为本功能提升库存交换协议版本。

## 10. 管理员集成 Token

建议新增小型目录集成 Token 服务，绑定管理员用户，不绑定个人游戏子账号。复用项目现有用户身份与管理员授权服务，不把新权限塞入普通个人 Token 的可选 scopes。

- 持有 `operator_catalog:write` 的管理员可创建、列出、撤销自己的集成 Token。
- 建议专用 scope 为 `operator_catalog:pools:write`，允许卡池查询、新建、编辑及附带的最小草稿创建。
- 每次调用既验证 Token，也验证所属用户仍激活并仍有 `operator_catalog:write`；撤销 Token 或取消角色后立即不可用。
- 插件权限不含发布密探、任意修改职业等普通资料、删除密探或管理其他管理员。
- 首版插件不提供整次卡池删除能力；误录删除在管理员界面完成。
- 集成入口建议放在 `/open-api/operator-catalog/operators`（供 ID/名称查找）与 `/open-api/operator-pools`（列表、详情、创建、修改），授权成功后调用相同服务。
- `/open-api/**` 现有配置允许进入控制器，必须在新入口执行集成 Token 校验，不能误当成匿名可写。

## 11. 实施顺序与交付物

### 阶段一：字段、状态与目录读取

增加实体/DTO 默认值、草稿校验、缺失字段提示、明确的管理和公开查询。修改普通资料及头像保存方式，确保卡池和状态不会被覆盖。处理种子默认已发布，保留历史待维护条目。

### 阶段二：卡池服务和自动创建

实现名称解析、编号分配、嵌入式副本写入、聚合查询、成员调整、复刻新建、整次删除及幂等持久记录。完成真实事务回滚验证。

### 阶段三：管理 API 和组合保存

实现卡池管理接口、密探组合编辑接口和发布接口。组合保存复用已有领域操作，整体原子提交。补齐成员/游戏约束及密探删除对卡池的影响。

### 阶段四：用户业务可见性和目录来源统一

覆盖养成导入、标注、目标、快捷提升、本体/SP 自动关联、公开分享和导出路径。库存 `agent` 查询/校验改读已发布密探，删除重复密探资源与播种逻辑，组合两类目录版本；切换前按实际 ID 差异保留有效存量对象。验证发布、改名即时影响心纸目录，物品目录行为不变。

### 阶段五：集成 Token 与 AstrBot API

实现管理员 Token 生命周期及逐请求权限校验，接入共享查询/创建/编辑服务。插件通过草稿查询复用已录入的新密探。

个人抽卡的 `/open-api/gacha` 使用子账号 Token 与 gacha scopes，属于另一份开发计划，不复用管理员公共卡池 Token 的权限。

### 阶段六：契约与开发文档

更新 OpenAPI 注解、`backend-openapi.json` 和 README 管理接口说明；产出前端对接说明及正式 AstrBot 接入文档。正式文档使用实际响应包裹、字段名、错误码和通过测试的请求示例。

## 12. 验证计划

以下为实施时需要的行为测试，不在纯文档阶段运行后端测试。失败时修正对应行为后再继续交付，不以模拟仓储测试代替 Mongo 事务验证。

| 要检测的失败 | 验证与处理方向 |
| --- | --- |
| 普通编辑或头像上传清空卡池/状态 | 保留字段与并发保存测试；改成字段级更新或事务内合并 |
| 如鸢延期误改代号鸢或复刻覆盖实装 | 同名跨游戏、多次开放测试；严格按稳定 ID 修改 |
| 成员更新与延期后各副本不同 | 多成员修改及交错请求集成测试；修正事务内成员解析与写入 |
| 一位写入失败却留下其他副本或新草稿 | 在 replica set 环境注入中途失败；确认整批回滚 |
| 重试重复创建、同键不同正文覆盖旧结果 | 创建/成员新增重试、服务重启后重试测试；修正持久去重 |
| 多入口自动分配重复编号或覆盖旧密探 | 并发创建、手工编号后自动创建测试；修正计数器和唯一性 |
| 按名字误用 SP/跨游戏重复建人 | 草稿复用、精确匹配、多候选、重复成员测试 |
| 草稿通过直接 ID 或 SP 自动关联进入用户养成 | 公共读取与各写入口契约测试；修正已发布查询调用点 |
| 公开卡池聚合泄漏草稿成员或管理员删除卡池清掉个人记录 | 用户侧成员过滤、全草稿池可选性与历史保留测试；修正公开投影及删除边界 |
| 老目录突然隐藏或卡池编辑被历史缺失字段拦截 | 无新字段老文档、奇闻名称缺失条目测试；修正默认值及分层校验 |
| 发布后心纸目录仍未知、改名不同步或草稿提前可关注 | 发布/改名前后目录、关注、库存导入测试；修正唯一来源查询和已发布过滤 |
| 遗留 `entity_catalog.agent` 行仍参与查询或校验 | 构造两边名称不同及只有旧副本的条目；确认运行时只认密探目录 |
| 首次访问库存导致密探为空，或统一来源误改物品目录 | 空库从库存入口访问以及物品查询/校验测试；修正初始化调用及按类型取数 |
| 切换后有效存量密探消失 | 一次实际库 ID 差异核对及相应存量处理测试；保留有效原 ID，不自动复活已删除密探 |
| 普通个人 Token 写公共目录，或管理员撤权后仍可写 | 认证契约测试；修正专用 Token 与当前权限检查 |
| 事务失败或重启后目录版本错误 | 回滚和重启读取测试；版本与数据同事务持久化、提交后更新内存 |
| 库存目录只随一个来源变化而更新版本 | 分别变更物品版本和密探版本；确认组合版本均变化且接口结构保持不变 |
| 边界时间错一秒/八小时 | `+08:00` 往返、`Z` 输入、起止相等及 `[start,end)` 边界测试 |

完成标准：两种管理员编辑入口及插件调用同一服务，所有已确定行为有对应实现与必要验证，最终接入文档与真实 API 一致。实际生产 Mongo 的事务部署条件在实施/部署阶段核对；仓库开发 compose 已配置 replica set。
