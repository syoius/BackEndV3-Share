# AstrBot 个人抽卡记录：功能与接入计划

日期：2026-09-09。状态：功能记录及接口计划，后端与插件尚未实现。具体命令文本、参数和响应包裹以后续正式接入文档为准。

相关文档：[后端开发计划](./gacha-records-backend-plan.md)、[网页交互规格](./gacha-records-frontend-spec.md)。管理员维护公共卡池的插件能力见 [另一份说明](./operator-catalog-up-pools-astrbot-notes.md)，不要混用身份和 Token。

## 1. 功能范围

| 场景 | 插件操作 | 后端行为 |
| --- | --- | --- |
| 查询可记录卡池 | 按游戏、名称查询并让用户确定目标 | 返回公开卡池、稳定 pool_id、可用规则和成员 |
| 首次记金 | 确定卡池、首条是否必 UP、密探及抽数 | 创建本人绑定子账号的档案，校验完整序列 |
| 追加一金 | 传结果密探和本次间隔抽数 | 在当前序列末尾追加，自动判断 UP 和下一条约束 |
| 修改/删除一金 | 先查稳定 record_id，再提交操作 | 按最终序列重新校验；冲突则整次拒绝 |
| 历史补录/排序 | 查询完整档案后修改顺序 | 复用整池批量保存契约，不按消息时间排序 |
| 查看单池 | 查询档案及统计 | 返回有序金卡结果、已记录抽数、不歪率等 |
| 查看全卡池 | 查询当前绑定子账号和选定游戏 | 合并各池统计，按总分子分母计算不歪率 |
| 记录额外自选 | 选择受支持的奖励及密探 | 写独立奖励列表，不增加抽取次数或重置状态 |
| 导入/导出 | 处理完整池档案文件 | 复用后端抽卡协议及权限、顺序、规则校验 |

不实现实时垫抽命令，不接受未知抽数，不逐抽记录三星/四星。个人记录操作不创建公共密探、修改 UP 名单、发布草稿或自动增加库存/养成。

首版可以先交付查询、末尾追加、修改/删除及统计；复杂补录/排序使用同一后端能力，插件交互若尚未实现则明确引导网页，不声称已经支持。导入导出在后端协议定稿后接入。

## 2. 个人身份与授权

- 使用现有绑定游戏子账号的个人 OpenAPI Token，建议新增 `gacha:read`、`gacha:write`、`gacha:export` scopes。
- 查询记录和统计需 read；写入/删除/导入需 write；文件导出需 export。插件常用记录流程通常需要 read + write，不能假设 write 自动包含 read。
- 目标用户、子账号由 Token 决定，不接受聊天中提供任意用户 ID。切换子账号应切换用户已配置的对应 Token。
- 同一个机器人服务多个用户时，各聊天用户使用自己的绑定；不能把机器人的管理员 Token 当作所有人的个人身份。Token 配置和回显不放到群聊公开消息中。
- 管理员公共卡池集成 Token 不授权访问个人记录；普通个人 Token 也不能维护公共卡池。两条流程可以存在于同一插件，但配置和请求路由分开。

## 3. 一次正常记金的流程

1. 确认用户绑定账号和游戏，查询并解析卡池；同名多次开放必须选择具体 pool_id，不能只取第一个匹配。
2. 查询单池最新档案、revision 和推导出的下一条是否必 UP。新档案询问首条记录前的必 UP 状态；不能从“这次出了 UP”反推。
3. 将输入名称解析为公开密探 ID。唯一精确匹配可采用，多候选请用户选择；不存在则提示目录未收录，不走管理员自动创建。
4. 要求用户提供游戏显示的“X 抽出金”，普通 UP 为 1～40。日期可省略，抽数不可省略。
5. 在必 UP 状态只提供本池 UP 候选；后端仍按最终序列校验。名称输入与必 UP 冲突时解释原因，不自动替换密探。
6. 生成稳定 record_id 和 request_id，提交末尾追加请求。只有后端成功才回复“已记录”。
7. 使用服务端返回的单池统计回复，可包含密探、抽数、是否 UP、单池已记录抽数和不歪率；不把手工记录误称为账号全部实际抽数。

## 4. 请求示意

建议末尾追加使用 `POST /open-api/gacha/pools/{poolId}/records`，Header 为 `Authorization: Bearer <个人Token>`。以下只表达正文形状：

```json
{
  "request_id": "astrbot:draw-example-001",
  "expected_revision": 3,
  "record": {
    "record_id": "draw_example_4",
    "operator_id": "char_125_zhaoyun",
    "pull_count": 18
  }
}
```

首次创建普通 UP 档案时还需要 `initial_guaranteed_up`，不存在的档案 expected_revision 为 0；已有档案的普通追加不能顺便改起始状态，修改该状态应走明确的档案编辑。

不提交 `is_up`、统计值、用户 ID 或 account_id 覆盖 Token 归属。示例卡池和密探是否可用以真实目录为准。

补录/排序复用整池保存，请求包括最终完整 `records`、`selection_rewards`、初始状态及最新 revision，不能仅把新增一条当完整列表发送。

## 5. 重试、重复消息与并发编辑

- 插件为一次明确操作持久保留 request_id、record_id 和原正文；消息被重复投递、HTTP 超时或连接失败时用原值重试。
- 可将平台消息/事件 ID 与命令操作标识关联保存；一次新记金操作使用新 ID，不能按“密探+抽数”去重，因为确实可能连续两次相同结果。
- 相同请求重试返回原结果，不重复追加。用户编辑或删除后再重放旧消息，也不能恢复旧记录。
- 真正的 revision 冲突先重新读取：普通追加在重读后需要重新验证最新状态和用户意图；涉及删除、补录或覆盖不自动重放旧列表。
- 后端报告第 N 条必 UP 冲突时，提示检查前面漏记、顺序或结果；不要关闭规则校验来强行保存。
- 导入文件重复提交沿用同一请求 ID；有意覆盖新版本时使用最新 revision 和新请求 ID。

## 6. 统计回复口径

单池和全池均使用后端统计，不在插件中重新平均各卡池比率。“不歪率”只统计非必 UP 判定中的 UP 成功比例，不包含歪后必 UP；无样本回复“暂无数据”。

全池范围是 Token 绑定子账号和所选游戏，常驻/特殊池参与基础抽数和金数，普通 UP 不歪率只覆盖适用池。不专门突出“歪的次数”，可显示“不歪率 60%（3/5 次）”。

实际日期未知的记录可以无日期保存，不用消息日期冒充发生日期。日期筛选的统计和排除数量直接采用后端返回值。
