# 个人抽卡记录与统计：后端开发计划

日期：2026-09-09。状态：已确认需求的开发计划，尚未实现。接口、集合与字段命名为实施建议，正式契约以后端实现及 OpenAPI 为准。

相关文档：[公共 UP 卡池计划](./operator-catalog-up-pools-backend-plan.md)、[前端交互与统计说明](./gacha-records-frontend-spec.md)、[AstrBot 个人抽卡记录功能](./gacha-records-astrbot-notes.md)。

## 1. 已确认的范围

- 用户按自己的游戏子账号记录抽卡，沿用现有统一子账号，不新增抽卡专用账号体系。
- 一条普通抽卡记录表示一次出金：选择一位 `rarity=5` 的绝密密探，填写游戏记录显示的本次出金间隔抽数。同池允许多条、允许重复获得同一密探。
- 抽数必填且为正整数，不支持未知抽数。不记录三星/四星及逐抽结果，不维护实时垫抽。
- 记录可以编辑、删除、补录和调整顺序；前端操作，后端保存最终顺序并校验最终序列。
- 自动推导普通 UP 池的保底状态，前端据此限制候选，后端在保存和导入时执行相同语义的校验。
- 提供单池统计及当前子账号的全卡池汇总；对用户使用“不歪率”一词，不单独突出“歪的次数”。
- 支持个人记录导入、导出；预留并计划实现 AstrBot 查询、录入和修改个人记录的 API。
- 普通 UP、常驻及特殊池可以出现在同一个记录页面；额外自选奖励与抽取出金分开。

本功能只维护个人抽卡事实，不改养成等级、招募状态、心纸数量或库存奖励流水，不向公共目录创建密探。公共内容管理员没有因此查看他人记录的权限。

## 2. 玩法依据与本期边界

规则来自本次用户说明，未声称已经核验所有官方卡池公告：普通 UP 池最多 40 抽出一金；非必 UP 状态的出金有 50% 概率为 UP；同池最近一金非 UP，则下一金必为本池 UP 之一。提前出金也作为一次出金结果参与状态推导。

以下不能从已提供信息推断，实施时不得自行补成通用规则：

- 不自动跨不同 `pool_id` 继承保底状态，不根据池名或复刻关系连接个人记录。
- 首条记录的状态由档案的 `initial_guaranteed_up` 明确提供；中途开始记录同样必填。只有确认某池开池规则后，前端才可为“从第一金记录”预填该值。
- 若游戏显示的间隔抽数包含前一个池的投入，必须先确认边界口径；本方案的单池投入和全池合计以每条所填抽数不重复计入为前提，不自动拆分跨池抽数。
- 常驻、自 BAN 及其他特殊池不直接套用普通 UP 的 50%/歪后必 UP 规则；其最大间隔也须按已确认规则校验。规则未确定时只要求正整数并做基础统计，不虚构上限或不歪率。

第一版每池档案是一段连续的出金序列。抽数即使准确，也不能证明中间没有漏金；界面提示完整性要求，后端检查可判定的规则冲突，不承诺检测所有遗漏。暂不增加多段序列、实时计数或跨池保底追踪。

## 3. 可记录卡池目录

新增 `GachaPoolCatalogService` 作为查询服务，聚合不同来源，不重复保存普通 UP 卡池主数据：

| 类型 | 来源与规则 |
| --- | --- |
| `ordinary_up` | 从密探 `up_pools` 按 `pool_id` 聚合，复用公共卡池服务；启用已确认的普通 UP 规则 |
| `permanent` | 每个游戏独立的稳定常驻池条目；没有结束时间，不参与不歪率 |
| `special` | 单独的轻量卡池条目，保存名称、游戏、开放时间及已确认的具体能力；不写入每位密探的 `up_pools` |

常驻和特殊条目建议使用小型 `gacha_other_pools` 集合，由 `operator_catalog:write` 管理员维护；只存这些池，不复制普通 UP 池。使用具体字段表示已确认的抽数上限、是否提供额外自选奖励，不建设通用规则引擎。自 BAN 名单若以后需要保存，属于用户个人选择；首版不做其概率分析。

用户查询仅返回公开可用的资料，普通 UP 成员过滤草稿。若全部 UP 成员均未发布，该池不作为新建个人档案的可选池。结果选择范围为该游戏已发布的绝密密探；普通状态可以选非 UP，必 UP 状态只能选本池公开 UP。

补录可以选择已结束的卡池，录入时间不必位于开放期间。实际获得日期选填，不用录入时间替代。常驻池在两个游戏中使用不同 ID；名称不是卡池主键。

## 4. 私人数据模型

建议一个 `(userId, accountId, poolId)` 对应一份 `gacha_pool_logs` 文档，唯一索引约束该三元组。文档保存按实际先后排列的出金数组及独立自选奖励数组，修改单池档案可以原子替换。

| 档案字段 | 语义 |
| --- | --- |
| `user_id` | 登录态或 Token 所属用户，不能由正文指定 |
| `account_id` | 已校验归属的统一子账号 |
| `pool_id` | 公共/可记录卡池的稳定 ID |
| `game` | 创建时由卡池确定，之后不随子账号设置改写 |
| `initial_guaranteed_up` | 普通 UP 池首条记录之前是否必 UP，布尔必填；其他池为 null |
| `records` | 按实际出金顺序排列的数组，数组位置是唯一顺序来源 |
| `selection_rewards` | 额外自选奖励，独立于出金序列 |
| `pool_snapshot` | 首次记录时的游戏、类型、名称、必要规则及公开 UP ID，供历史回退，不是公共目录 |
| `revision` | 乐观并发版本，防止网页和 AstrBot 互相覆盖 |
| `created_at / updated_at` | 系统维护的录入/修改时间 |

每条 `records` 包含：

- `record_id`：调用方生成的稳定 UUID 或等价不重复 ID。对同一用户/子账号保持唯一，移位及编辑不换 ID；同一密探多次出金使用不同 ID。
- `operator_id`：一位绝密密探的 ID；不使用名字作身份。
- `pull_count`：包含出金这一抽的间隔抽数；普通 UP 池为整数 `1..40`，不接受 0、null 或缺失。
- `occurred_at`：实际出金时间，可选，带时区；未知日期可以省略，未知抽数不可以。
- `note`：可选备注。
- 服务端维护的录入/更新时间、历史展示名称，以及已验证的结果归类 `is_up`；非 UP 规则池的 `is_up` 为 null。

`is_up` 新建或改换结果密探时由后端按卡池名单计算，不采信普通写入请求中的布尔值。`guaranteed_before` 是基于完整顺序推导的响应字段，不单独保存以免顺序改变后失效。

每条额外自选奖励保存稳定 `record_id`、所选密探、实际领取日期/备注及奖励档位，例如 `milestone_pulls=300`。没有 `pull_count`，不是“未知抽数的出金”；不能混入 `records`。仅已确认提供该奖励的特殊池可以填写，按其规则限制领取次数和选择范围。

### 4.1 身份和生命周期

- 创建新档案时校验卡池游戏与目标子账号当前游戏一致。子账号改游戏不搬迁、重标或删除旧档案；旧档案按保存的游戏查询和维护。
- “全卡池”默认表示当前子账号、当前选定游戏的全部卡池，不自动合并不同子账号。切换到历史游戏可以查询原记录。
- `SubAccountService.delete()` 增加该账号抽卡档案及写请求去重结果的级联删除，复用现有事务和归属检查。
- 后端每个记录、统计、导入、导出入口都限定用户和子账号；传入其他人的记录 ID 不会获得访问权。

## 5. 前后端共同遵循的状态推导

按 `records` 数组顺序，从 `initial_guaranteed_up` 开始：

```text
guaranteed = initial_guaranteed_up
对每条出金：
    before = guaranteed
    如果 before 为 true 且本条不是 UP：返回本条的规则错误
    如果 before 为 false：本条计入“不歪率”的判定样本
    如果 before 为 false 且本条是 UP：计为一次不歪成功
    guaranteed = 本条是否非 UP
```

前端使用该逻辑即时调整候选和显示冲突；后端使用领域纯函数在保存、导入和统计中复用同一算法。前端计算值不是后端授权或校验结果。用相同示例数据验证两端结果，避免分别解释规则。

删除、插入、修改和排序后校验最终完整序列，不只校验被编辑的行。例如“非 UP、UP、非 UP”删除中间一条后非法，应返回对应 `record_id`、数组位置及错误原因，整次保存失败。前端保留本地修改，不替用户改成另一个密探。

时间筛选用于选取统计结果，不能先截掉前面的记录再推导保底。先按完整档案推导每条是否为非必 UP 判定，再筛选日期和聚合。

## 6. 保存接口与重试

### 6.1 网页批量保存

建议 `PUT /v1/gacha/pools/{poolId}/log?account_id=...` 提交该池最终完整档案内容，缺失于最终数组的旧记录视为用户删除。请求必须同时包含 `records`、`selection_rewards` 和初始状态，不能把局部数组当完整档案覆盖。这是私人单池档案的保存契约，与公共卡池的局部更新契约不同。

示例省略自选奖励内容：

```json
{
  "request_id": "web:save-example-001",
  "expected_revision": 0,
  "initial_guaranteed_up": false,
  "records": [
    { "record_id": "draw_example_1", "operator_id": "char_001_yangxiu", "pull_count": 32 },
    { "record_id": "draw_example_2", "operator_id": "char_125_zhaoyun", "pull_count": 18 }
  ],
  "selection_rewards": []
}
```

示例假定该池赵云为 UP、杨修非 UP，并且二者已公开可选。第一条非 UP 后第二条必 UP；两条合计 50 抽，非必 UP 判定为 0/1，总 UP 占比为 1/2。示例 ID 仅表达请求形状，不宣称该实际卡池已经存在。

不存在的档案按 revision 0 创建；成功写入递增 revision。条件更新失败返回 `409 revision_conflict`，要求重新读取后处理冲突，不能用旧表单静默覆盖新记录。原样内容保存不增加业务记录。

### 6.2 AstrBot 逐条操作

提供末尾追加出金、按 ID 修改/删除，以及查询当前档案的接口；服务在事务内读取最新序列，应用操作，再执行与批量保存相同的完整校验。补录与复杂排序可以复用批量保存接口，无需另写一套规则。

所有写操作携带稳定 `request_id` 和期望 revision，响应丢失后使用原请求重试。持久去重以用户、子账号、操作与请求 ID 为范围，比较规范化业务字段而非哈希：同键同内容返回原结果，同键不同内容返回冲突。查重应先于旧 revision 判断，避免已成功请求的重试误报版本冲突。

写请求结果与档案修改在同一事务中提交；请求后来被其他编辑覆盖或记录被删除，重放旧请求不能重新追加或恢复删除的记录。复用已有 Hub Mongo 事务，无需 Redis 充当唯一去重来源。并发两个真实的新请求发生版本冲突时重新读取，不自动猜测用户想要的顺序。

## 7. 单池与全卡池统计

统计按实际记录查询计算，不持久化一份容易与编辑结果脱节的汇总。响应同时提供合计和各池摘要，前端不自行平均各池比率。

| 指标 | 口径 |
| --- | --- |
| `recorded_pulls` | 所选抽取出金记录的 `pull_count` 之和；不含最后一金后的垫抽 |
| `gold_count` | 抽取出金条目数，不含额外自选 |
| `average_pulls_per_gold` | recorded_pulls / gold_count；无记录为 null |
| 中位数/最小/最大间隔 | 从所选出金记录计算；无记录为 null |
| `up_gold_count` | 适用普通 UP 规则的记录中 UP 数；特殊池不冒充普通 UP |
| `up_rate` | 普通 UP 记录的 UP 数 / 对应出金数，不拿它与 50% 比较 |
| `non_guaranteed_count` | 完整序列推导后，出金前非必 UP 的判定次数 |
| `non_guaranteed_up_count` | 上述判定中得到 UP 的次数 |
| `non_loss_rate`（不歪率） | non_guaranteed_up_count / non_guaranteed_count；分母为 0 时 null |
| 参与卡池数 | 筛选后有抽取出金记录的不同 pool_id 数；自选奖励单独列出 |
| 密探分布 | 各密探抽取获得次数；自选获得次数另列，不混成抽取次数 |

全卡池平均值从总和和总条数计算，不平均各池均值；不歪率从各池分子/分母之和计算。例如 1/1 与 1/9 汇总为 2/10=20%。常驻和特殊抽取结果可以参与总抽数/金数，不参与普通 UP 不歪率；响应标明指标适用范围。

不单独突出“歪的次数”，但后端可保留计算所需计数。不歪率在界面显示百分比与样本数；有限的手工记录不被解释成游戏真实概率或欧非评分。

日期按实际 `occurred_at` 以北京时间统计，区间采用 `[from,to)`；无日期记录计入不筛日期的总览，启用日期筛选时排除并返回排除数量。不得用 `created_at` 或卡池开始时间替代实际获得时间。

额外 300 抽自选不增加 300 抽投入、不增加金数、不改变序列状态。没有维护完整投入时，不根据已记录抽数不足 300 就断言用户不可能领取；仅按已确认奖励规则校验条目。

## 8. 公共卡池变更与历史保留

公共卡池改名/延期不改变用户记录的抽数、密探或顺序。卡池、成员或密探目录删除后，不级联删除个人抽卡档案；通过保存的名称等历史资料展示，并标注目录对象缺失。

正常显示优先使用现有目录名称；目录缺失时使用服务端录入时保存的回退资料。历史 `is_up` 归类保留录入时已验证的结果，不因管理员事后调整名单而静默重算全部个人历史。用户改换某条结果密探时按可用权威规则重新校验；未改结果的历史记录保留原归类。

目录存在时新增记录以当前公开目录校验，不接受客户端快照覆盖其规则。目录缺失时已有档案可以读取、导出、删除或重排既有结果；新增结果不凭私有快照创建公共对象。修正引用目标需要用户显式选择有效卡池/密探，不按同名自动迁移。

首次记录时保存必要的历史规则和已公开 UP ID，是为导出回读与目录删除后的历史解释，不构成第二个公共密探目录。草稿名称及管理字段不写入用户可见快照。

## 9. 导入、导出

使用独立格式，建议 `format=myshare-gacha-records`、`version=1`。不套用库存的 `reward_delta` / `stock_snapshot` 或密探养成交换协议。

- 一份文件表示一个子账号的抽卡记录，包含游戏、按池组织的初始状态、稳定记录 ID、明确数组顺序、抽数、可选日期/备注、自选奖励及必要历史回退资料。
- 文件中的账号信息仅用于辨识来源；JWT 调用显式选择自己的目标账号，Token 调用固定为其绑定账号，不采信文件中的内部用户归属。
- 导出所有池或明确指定的池；不导出计算出的统计作为可写事实，也不让日期筛选后的零散记录冒充完整连续档案。
- 导入以列出的池为完整覆盖单位，未列出的池保持不变。网页先展示影响并取得目标池当前 revision，再以明确的覆盖操作提交；重复记录不靠名称去重。
- 导入调用与编辑相同的字段、顺序、状态及权限校验。整份导入包含多个池时事务内整体提交，出错返回池 ID、记录 ID/位置，不部分落库。
- 目录仍存在的池和密探按权威目录验证。文件中的历史归类与当前规则不一致时报告冲突供用户处理，不静默改写；同一后端已存的未改动历史记录可沿用已验证归类。
- 若导出后公共对象被删除，允许将文件中的历史内容作为“目录缺失”的私人历史档案恢复并按其明示的已知规则做内部一致性校验；只能证明文件内部一致，不能声称已由当前目录核验。不得借此创建公共目录或开放基于缺失对象的新录入。
- 写请求去重、目标池 revision 和稳定记录 ID共同防止文件重传导致重复出金或覆盖较新编辑。请求重放返回原导入结果，后续有意再次覆盖使用新请求 ID及最新 revision。

实现阶段补充该格式的 JSON Schema 和完整往返示例；它是新增抽卡协议，不修改库存标准。

## 10. 建议 API 与权限

公开目录：`GET /v1/gacha/pools`、`GET /v1/gacha/pools/{poolId}`，包含卡池资料、类型、规则、可公开 UP 成员，不含任何用户统计。

JWT 私人接口建议：

| 接口 | 用途 |
| --- | --- |
| `GET /v1/gacha/logs?account_id=...&game=...` | 已记录卡池列表与摘要 |
| `GET /v1/gacha/pools/{poolId}/log?account_id=...` | 单池有序档案、revision 和推导状态 |
| `PUT /v1/gacha/pools/{poolId}/log?account_id=...` | 最终档案批量保存，含删除和重排 |
| `POST /v1/gacha/pools/{poolId}/records?account_id=...` | 末尾追加一条出金 |
| `PATCH/DELETE /v1/gacha/pools/{poolId}/records/{recordId}?account_id=...` | 修改/删除指定出金，仍校验整池序列 |
| `GET /v1/gacha/statistics?account_id=...&game=...` | 全池合计与逐池摘要；可筛 pool_id、类型、日期 |
| `GET /v1/gacha/export?account_id=...` | 导出所选完整池档案 |
| `POST /v1/gacha/import?account_id=...` | 显式覆盖所列池，整体校验保存 |

OpenAPI 使用 `/open-api/gacha/...` 对应入口，从个人 Token 取得目标账号，不提供跨账号参数。建议扩展现有 `OpenApiPermission`：`gacha:read` 用于记录/统计查询，`gacha:write` 用于录入/修改/删除/导入，`gacha:export` 用于文件导出。管理员公共卡池集成 Token 不具备这些个人数据权限。

建议错误：401/403（认证/权限）、404（账号/池/记录不存在）、409 `revision_conflict` / `request_conflict`、422 `invalid_pull_count` / `invalid_operator` / `guaranteed_up_required` / `invalid_record_order` / `invalid_initial_state`。后端响应使用项目统一包裹，错误提供可定位的池和记录信息。具体路径、错误码和 DELETE 请求的去重/revision 参数传递方式在 OpenAPI 中定稿。

## 12. 必要验证

纯文档阶段不运行后端测试；实现时每项验证针对下面的实际失败：

| 要检测的失败 | 验证重点与修正方向 |
| --- | --- |
| 抽数缺失、0 或普通 UP 超过 40 被接受 | 各入口共享字段校验；未知日期不能被误当未知抽数 |
| 必 UP 状态仍能选择非 UP | 初始状态、连续歪、前后端同样例；后端拒绝非法最终序列 |
| 删除/重排后规则冲突仍保存 | 批量和逐条操作都对最终序列重新校验且原子提交 |
| 日期筛选使首条被误判为普通状态 | 完整推导后筛选，包含筛选窗口之前的保底影响 |
| 将各池比例平均、把必 UP 当作不歪成功 | 使用 1/1 与 1/9 等样例，按分子分母汇总 |
| 0 样本显示 0%，或无日期被归到录入月份 | 空值和日期缺失语义测试 |
| 300 抽奖励重复算投入、金数或重置保底 | 独立奖励数组及统计隔离测试 |
| 网页与 AstrBot 同时改动造成覆盖 | revision 条件更新与冲突返回测试 |
| 超时重试追加两次、删除后旧请求复活记录 | 请求去重与修改原子提交；重放先于 revision 检查 |
| 导入丢顺序、重复记录或多池部分成功 | 完整导出往返、重复导入及中途失败回滚测试 |
| 草稿泄漏、普通记录创建公共密探、Token 跨账号 | 已发布筛选和各入口身份权限契约测试 |
| 卡池改名/删除后个人记录丢失或统计变化 | 历史展示与归类保留、目录缺失恢复测试 |
| 删除子账号留下个人档案或去重记录 | 与已有级联事务一起验证 |

验收结果应覆盖单池记录页、全池总览、网页修改、文件往返与 AstrBot 重试这几条实际使用路径，不以只有前端候选限制代替后端校验。
